# bob's game — Project Architecture & Memory Observations

## 1. Monorepo & Submodule Strategy
The project follows a strict multi-repository "Omni-Workspace" approach containing multiple parallel ports, designed for maximum feature parity:
- **`bg/`** (Root Workspace): Houses overarching documentation (AGENTS, ROADMAP, DEPLOY) and coordinates the submodules.
- **`bobsgameweb/`**: The active TypeScript + Vite + PixiJS v8 port. This is the primary target for current active feature development and acts as the "web engine" capable of being packaged to Desktop/Mobile via Electron/Capacitor.
- **`okgame/`**: The native C++20 + SDL3 engine.
- **`bobsgameonlinejava/`**: The legacy Java 21 + LibGDX version serving as the primary reference point during TS porting operations.
- Git operations across submodules must explicitly sync origin trackers using `--remote --merge` to preserve local feature branch nuances and upstream history.

## 2. Core Architectural Decisions (TypeScript Port)
The web port recently completed Phase 2 (Game Loop Integration) where legacy scene-based flow (`StateManager.push(MainMenuScene)`) was replaced with a monolithic native engine loop (`ClientGameEngine`).

- **`ClientGameEngine`**: The core execution context. Handles updating systems (`MapManager`, `EventManager`, `NetworkManager`) and renders the overarching world natively instead of routing through empty PIXI scenes.
- **`ND` Console Layer**: A virtualized "secondary console" overlay embedded inside the PIXI container. The nD handles secondary rendering elements like the core puzzle mechanics (`BobsGame`), meaning the primary RPG world can freeze or stay active underneath it. We recently implemented an OS shell (`NDOS.ts`) inside the ND to select between mini-games.
- **`BobsGame` (Puzzle Engine)**: Decoupled into `GameLogic` and `PuzzlePlayer` objects, meaning it operates entirely functionally detached from PIXI until `PuzzleRenderer` attaches and echoes the state. This enables replay logging and server-side logic validation without tying it directly to DOM/Canvas ticks.

## 3. Code Porting & Syntax Patterns
Several strict boundaries map original Java/C++ code semantics into TypeScript:
- **`private` to `protected`**: Fields often need to become protected for inheritance behaviors which previously utilized friend classes in C++.
- **Single-Threaded Contexts**: Heavy threaded logic like UDP handling in `PeerConnection.cpp` are mapped to WebRTC DataChannels or Socket.io events. `synchronized` Java wrappers are replaced with asynchronous promises.
- **PIXI v8 Limitations**: `Graphics` context drawing must favor the v8 API logic (`rect`, `fill()`, `stroke()` objects) instead of the deprecated v7 syntaxes (`drawRect`, `beginFill`).
- **Static vs Dynamic Imports in Hot Loops**: Dynamic chunks via `import()` inside `update(dt)` cause Vite pipeline bloat and flickering frame drops. Imports must be hoisted and declared statically for classes like `InputManager` running every tick.

## 4. Subsystems
- **InputManager**: Global event sink. Key states must explicitly map to player controllers in nested game objects (e.g. `isKeyHeld`, `isUpHeld`) instead of relying on decoupled callbacks.
- **MapManager**: Handles PIXI layer generation based on parsing `MapData` JSON representations. Collisions map locally by clamping coordinate boundaries directly inside the engine loop.
- **EventManager & UI**: `GUIManager` owns elements like `DialogueBox`. Events dynamically evaluate distance (e.g., `dist < 50`) mapped to physical `Graphics` models serving as NPCs on the world grid.
- **NetworkManager**: Connects directly to Socket.io (`ws.bobsgame.com`). Manages lobby representations asynchronously passing room events into `BobMenu` instances dynamically in `BobsGame`.
- **TournamentManager**: Hooks deeply into multiplayer sockets dynamically rendering brackets in production.

## 5. Deployment Rules & Constraints
- **Vite Build Process**: Must use `npx vite build` directly. Running `npm run build` triggers a Windows/Cygwin crash regarding heap size allocation for TS files.
- **Production Server (ws.bobsgame.com)**: Backend deployment operates via tarball to avoid SSH synchronization glitches (`BACKEND_FORCE_TAR=1`).
- **Versioning**: Incrementing the version relies on a "Single Source of Truth." Any bump must natively update `VERSION.md`, `CHANGELOG.md`, `SUBMODULE_DASHBOARD.md`, and `package.json` to keep health endpoints completely mirrored.

## 6. Development Lifecycle (AGENTS / HANDOFF)
- Changes are fully autonomous but must prioritize safety (e.g., no `taskkill` which might drop IDE connections).
- Phase states must be continually tracked inside `TODO.md` and `ROADMAP.md` matching progress directly.
- `HANDOFF.md` logs exact module counts, compilation success metrics, and immediately executable next steps for successive AI cycles.
